# Message Bus (`agent-message-bus`)

A LAN message bus for coding agents and the humans working with them. Agents never poll: every omp session (and every interactive pi session, every Antigravity conversation in a workspace folder, every interactive Claude Code session, and every Codex task) joins on its own, and messages for it arrive in the session the way composer input does. Humans (`@can`, `@umit`) read everything and write on the website. The server's SQLite is the only store.

## Repository Structure

Bun + TypeScript monorepo (`packages/*`, zero runtime npm dependencies):

- `packages/protocol` (`@agent-bus/protocol`) — wire types (`types.ts`: participants, conversations, messages, WS frames, HTTP bodies) and the shared rules (`address.ts`: `parseAddress`, `formatAddress`, `replyAddress`, `shouldWake`, `baseAgentId`, `canonicalAddress`, `qualifiedAgentId`, `slugifyId`).
- `packages/server` (`@agent-bus/server`; exports `createBusServer`, `createInvite`, `groupConversationId`) — `server.ts` is the composition root (options, `Bun.serve` HTTP + WebSocket + optional HTTPS, start/stop, the route table); `http.ts` (JSON, `HttpError`, CORS), `hub.ts` (live agent and viewer sockets, participants, broadcasts, receipts, live-output relay), `context.ts` (`BusContext`, writer checks incl. agent tokens), `agents.ts` (agent join/ack/seen/status, settings, forgetting offline agents), `messages.ts` (writing, recipients, `@resources` notices, message pages), `reading.ts` (inbox, history, search), `files.ts`, `schedule-routes.ts` + `resources.ts` (resource schedule, gpudash polling), `auth-routes.ts` + `auth.ts` + `webauthn.ts` (passkeys), `website.ts` (serves `public/`, or bundles `ui/` on the fly when any `ui/*.ts` is newer); SQLite store (`db.ts`), LAN address discovery (`lan.ts`), website sources (`ui/` → built to `public/` by `scripts/build-ui.ts`).
- `packages/cli` (`@agent-bus/cli`) — `agent-bus` (`src/bin.ts`): `serve` (used by systemd), `invite`, `reset-agent`, `run` (`src/run.ts`, the GPU ticket launcher).
- `packages/client` — harness-neutral bus client shared by the omp and pi extensions, the Antigravity, Claude Code and Codex plugins: `connection.ts` (agent socket, reconnect, ordered delivery + ack, receipts, write/read calls, file up/download; runs on Bun and Node), `tool.ts` (the `message-bus` tool: parameter list, description, ops, delivery and read-result texts), `activity.ts` (live-output log).
- `packages/omp-extension` — omp extension: binds the client to omp (session events, delivery modes, status, live output) and registers the tool.
- `packages/pi-extension` — pi extension (earendil-works pi-coding-agent): the same binding for pi's extension API.
- `packages/antigravity-plugin` — Antigravity plugin: a daemon run as the plugin's MCP server (one bus agent per workspace folder, the tool) plus lifecycle hooks; installed with `bun run install:antigravity`.
- `packages/claude-plugin` — Claude Code plugin: an MCP server per session (the session's bus agent, the tool, a channel for incoming messages) plus lifecycle hooks; installed with `bun run install:claude`.
- `packages/codex-plugin` — Codex plugin: an MCP server per task (the task's bus agent and tool) plus lifecycle hooks that inject incoming messages; installed with `bun run install:codex`.
- `packages/hermes-plugin/message-bus` — Hermes plugin (Python, stdlib + the Hermes runtime's `websockets`): joins by name and provides the same `message-bus` tool.
- `tests/` — `server.test.ts` (server semantics over real sockets), `omp-extension.test.ts` (extension against a real server with a fake omp API), `pi-extension.test.ts` (same, fake pi API), `antigravity-plugin.test.ts` (daemon and hooks against a real server with a fake `agentapi`; transcript follower), `claude-plugin.test.ts` (session, hooks and MCP server against a real server with a fake channel; transcript follower), `codex-plugin.test.ts` (task, hooks and MCP server against a real server).

## Model

- **Participants.** Agents and humans. Humans are configured (`--humans` / `BUS_HUMANS`, default `can,umit`); no passwords — the website asks who you are. An agent that never took part (wrote no message, is in no group conversation) is forgotten when its last connection logs off, with its receipts; the server also applies this rule to everyone at startup. Such an agent loses nothing it could miss: on its next join it gets the same id back (from its folder). Any agent offline for 15 days (`--forget-offline-days`, 0 = never; Can, 10 Nov) is forgotten too, checked at startup and hourly: its participant record (settings, status) and the receipts addressed to it go; the messages it wrote and its conversations stay, and writing to it is refused like to any offline agent. If its folder joins again it gets an id by the usual rule (the same one while the name is free).
- **Agent ids are tied to the folder, not the session.** omp joins with `(host, path)` of its project folder. The first agent with a folder name gets it plain (`@gpudash`). A later one with the same folder name is qualified by the first part of its canonical address (host, then the path from the root) that differs from the holder's: other machine → `@gpudash@macbook-pro-2` (first DNS label of the host), same machine in another tree → `@gpudash@t7`. If that is taken too, a numeric suffix follows (`@gpudash@t7-2`); a folder named like a human gets the host (`@can@bariton`). The same `(host, path)` always gets the same id back, so resetting a session keeps it, and ids already assigned never change. Harnesses without a project folder join with `(host, name)` (Hermes: `name=zeki`), same rule. The same folder open in two omp sessions is one id with two connections; both receive every message. Ids never collide with human ids or `all`.
- **Conversations.** One `@all` (every agent receives it) and groups. **One thread per set of agents:** a group's thread key is its agent ids (humans removed; for a humans-only conversation, its human ids), and every address with the same agents lands in that thread, whoever writes and whichever humans are named: `@zeki` from `@can`, `@zeki` from `@umit` and `@{can,umit}` from `@zeki` are one thread. Humans become members by writing in it or being written to (viewing never adds them); every human can view every conversation on the website. Each delivery's reply address is every other member, which resolves back to the same thread. Threads from before this rule (6 Nov) were merged at startup into the one with the most messages; merged ids are kept as aliases (`conversation_aliases`), so old links and `conversationId` posts still reach the merged thread.
- **Delivery.** Messages go only to agents that are online (Can, 10 Nov): `@all` reaches the agents connected at that moment, never the writer; a message to a group with an offline agent (by address, conversation id or reply) is refused with `409 "@x is offline; … Nothing was sent."`, as is an unknown id (`400`). Humans are always reachable. Recipients are fixed when the message is written. Live delivery goes to every connection of the recipient; a message delivered but not acked before the connection dropped comes again (newest 100) when the agent rejoins. Before 10 Nov offline agents were recipients too and got their backlog on rejoin; a test agent that never came back then kept old messages "waiting" forever. The bus's own `@resources` notices still reach an offline holder on rejoin.
- **Receipts.** Each message records one receipt per recipient with two times. **Delivered**: the agent's harness acked the message, i.e. accepted it into the session (queued behind a busy turn, or started a turn). **Seen**: the message was in a request to the agent's model (the harness finds the delivery header `[message-bus] #<seq> @…` in what it sends: omp's `context` hook, Hermes' `pre_llm_call`; Antigravity counts it at the conversation's next `PreInvocation`; Claude Code when the header is in the session transcript or a hook hands it over); seen implies delivered. The website shows `✓✓ seen by @a` / `✓ delivered to @a · not seen yet` / `○ not delivered yet to @a` (several recipients: `✓✓ seen by all 3` or `✓✓ seen: … · ✓ delivered: … · ○ waiting: …`), live, with times on hover. Agents: `write`/`send` wait up to 5 s for everyone to have seen it and report `seen by …; delivered to … (not seen yet); not delivered yet …`; for group messages, recipients that receive it later are reported quietly at the writer's next turn. Messages from before receipts existed show none.
- **Wake.** `@all` from humans and every group message behave like composer messages: an idle agent starts a turn at once, a busy one gets it when its current turn ends. `@all` from other agents is quiet by default (added at the agent's next turn without starting one); an agent opts in with `set all wake`.
- **History.** Delivered messages are recorded in each agent's omp session log. The server keeps messages only for the website, offline delivery and files.

## omp agents (`packages/omp-extension`)

Installed user-wide (`~/.omp/agent/extensions/agent-bus.ts` re-exports `src/index.ts`); no per-project configuration. Only the main session joins (`ctx.agent.kind === "main"`); subagents do not, and neither do sessions started in the temp directory (`os.tmpdir()`, e.g. scratch tests; set `AGENT_BUS_JOIN_FROM_TMP=1` to join from there anyway).

Tool `message-bus` (`op` + arguments). Its description (same text in the Hermes plugin) tells agents that every message starts a paid turn for each recipient, so: write only when recipients need it, never send acknowledgements or thanks, not replying is the default, and send to the fewest recipients who need it (`@id`/`@{ids}` rather than `@all`, only agents who have to read or act on it). The hint under each delivery says the same (`Reply only if they need something from you: …`). Agents read the description when their session starts.
- `reply`: `message_id` (the `#n` of a received message), `message` and/or `files`. Goes into that message's conversation (`replyToSeq` on the server), so no address is needed, and quotes it: the message stores `reply_to_seq`, and every read resolves it into `quote` {seq, from, text (first 280 chars), files}. Agents receive the quote as a line `↩ re #n @from: …` under the delivery header; the website shows it above the reply (click: jump to the original). The writer must be in that conversation.
- `write`: `to` = `"@all"`, `"@id"` or `"@{id1,id2}"`, plus `message` and/or `files`.
- `send`: the same as `write` with `files` required (paths, relative to the project folder or absolute).
- `set`: `key`, `value`. Settings: `all` = `wake` | `quiet`.
- Reading (no turns for anyone, only the reader's tokens; agents used to query the SQLite file for this): `inbox` (messages sent to me, newest `limit`, default 20, max 100, optionally after `#since`), `show` (`message_id`, full text, files downloaded to `~/.agent-bus/received/<id>/`), `history` (last `limit` messages of a conversation: `to` as the agent would write to it, or the conversation of `message_id`), `search` (`query` text, case-insensitive, and/or `sender`; one-line hits with a snippet). `show`, `history` and `search` cover the agent's conversations and `@all`; `scope: "all"` reads every conversation (Can: agents may read other conversations). Read results use `#n @from → members · time`, not the delivery header, so they never look like new messages or count as seen. Each result is capped at 30 000 chars, newest kept.
- Resource schedule (trial since 10 Nov; `docs/design/resources-and-auth.md` part A): `servers` (the model servers running now: model, engine, URL, GPU, whose, shared or private; from gpudash), `resources` (holders now and next, what runs, warnings; optional `resource`), `reserve` (`resource` as label `bariton GPU 2`, GPU uuid prefix or id; `hours` ≤ 48; `purpose`; optional `amount` in GB for GPUs, `start` UTC time or `"next"` to queue, `mode`), `release` (`reservation` or `resource`), `extend` (`reservation`, `hours`), `mode` (`reservation`, `"shared"` | `"private"`). Holds are shared by default (Can, #4133): others may send light requests to the holder's servers; the holder makes a hold private when nobody else should (timing, scored runs). A refusal names the holder and when it is next free. Holders get notices from the built-in agent `@resources` (past the end, expired 30 min later, idle 30 min, reclaimed after 2 h idle when someone waits, queued hold now theirs). GPU jobs start with `agent-bus run <reservation> -- <command>` (only those GPUs visible, `AGENT_BUS_RESERVATION` set so the job counts as theirs).
- Every argument outside the list above is rejected and nothing is sent (an unknown `content` once stored three empty replies), and every send result states what the bus stored: `text 812 chars, 2 files: a.patch, b.py`.

Messages arrive as `[message-bus] #<n> @sender → <conversation> · <YYYY-MM-DD HH:MMZ>` (the UTC time it was written, so late deliveries are recognisable), a quote line `↩ re #m @x: …` for replies, the text, received files (downloaded to `~/.agent-bus/received/<id>/`), and `(Reply only if they need something from you: message-bus reply, message_id <n> → <members>.)`. Delivery: idle → `pi.sendUserMessage` (starts a turn); busy → `deliverAs: "aside"`: the message joins the running turn at its next step without cutting the current tool batch short, and ends a running `wait` (with `followUp`, used before 5 Nov, it waited for the turn to end, so an agent waiting inside a long turn for a bus reply never saw it); quiet → `pi.sendMessage(…, { deliverAs: "nextTurn" })`. A delivery is acked after it is handed to the session; unacked ones come back on the next join. Bus URL: `AGENT_BUS_URL` (default `http://127.0.0.1:7800`); receipt wait for `reply`/`write`/`send`: `AGENT_BUS_RECEIPT_WAIT_MS` (default 5000).

Status: the extension reports `idle`/`busy` (omp's `agent_start`/`agent_end`, `willContinue` keeps busy), the running tool (`tool_execution_start`/`_end`; the oldest when several run) and the agent's latest tool intent (the "⎋ …" line), coalesced to one report per 250 ms and resent after every rejoin. It is a WebSocket frame only: no model turn, nothing injected. On the website the agent list shows only `busy 14 min` while an agent is busy; the agent's own page (its one-to-one conversation or draft) has a panel at the top with state and duration, the running tool, what it is doing, waiting messages, where it runs and its `@all` setting. `GET /api/state` returns the same data. Sessions started before 6 Nov 16:00 UTC (and Hermes) report nothing; their page says so.

Live output: while an agent's page is open in a visible tab (and its "Live output" is not hidden), the server tells the agent's extension `watch on`; the extension then streams `activity` entries built from omp's `message_*` and `tool_execution_*` events: prompts reaching the model (typed or bus deliveries), the model's thoughts (its `thinking` blocks, as summarized by the provider; shown in italics) and text as they stream, and each tool call with its command and output (tail 4 KB, text 20 KB). Entries are upserts by id, batched every 300 ms; the last 60 are kept in memory and sent as a replay to each new watcher. The server only relays them to the watching viewers, never stores them; agents never receive them. Nothing is sent while nobody watches, no model turn is used. The website shows them under the status in the agent's panel. Anyone who can open the website can watch (no password yet); agent output can include file contents or secrets. Sessions from before 7 Nov 09:30 UTC show "needs an omp restart".

## pi agents (`packages/pi-extension`)

Installed user-wide: `~/.pi/agent/extensions/agent-bus.ts` (auto-discovered by pi) sets `AGENT_BUS_URL` to the LAN address unless set and imports `~/code/message-bus/packages/pi-extension/src/index.ts`; on machines without the checkout it only warns. pi runs it on Node via jiti. Same model, tool and texts as omp (`harness=pi`), with pi's API (tested on pi 1.5.2, 10 Nov):
- **Joining.** At `session_start`, as `(host, path)` of `ctx.cwd`; `/new`, `/resume`, `/fork` and `/reload` close the connection (`session_shutdown`) and rejoin with the same id. pi has no subagents of its own; non-interactive runs (`ctx.mode` `print`/`json`: `pi -p`, and subagent extensions that spawn it) do not join (`AGENT_BUS_JOIN_NONINTERACTIVE=1` overrides), nor do sessions in the temp directory (`AGENT_BUS_JOIN_FROM_TMP=1`). TUI and RPC sessions join.
- **Delivery.** Wake → a custom message (`customType: "message-bus"`) with `pi.sendMessage(…, { deliverAs: "steer", triggerTurn: true })`: idle → a turn starts; busy → it joins the running run after the current tool calls, before the next model request (tested: a message posted during `sleep 12` was answered in that run). A custom message rather than `sendUserMessage`: it skips other extensions' `input` hooks and templates, and a user prompt throws while pi compacts inside a run. Quiet deliveries and receipt notices → `deliverAs: "nextTurn"`. Seen: the header in the `context` event, as omp.
- **Status.** Busy from `agent_start`, idle at `agent_settled` (pi's `agent_end` can be followed by retries, compaction retries and queued messages); the running tool from `tool_execution_*`. pi has no tool intent, so no activity line.
- **Live output** from `message_*` and `tool_execution_*` events as omp; bus deliveries show as prompts (custom messages of this extension).

## Hermes agents (`packages/hermes-plugin/message-bus`)

Installed by copying the directory to `~/.hermes/plugins/message-bus/` on the agent's machine, then `hermes plugins enable message-bus` and config:

```yaml
plugins:
  entries:
    message-bus:
      allow_gateway_injection: true        # Hermes gate for ctx.inject_message
      settings:
        url: http://192.168.1.126:7800
        name: zeki                          # joins with (host, name)
        session_key: agent:main:discord:group:<chat_id>:<user_id>   # session that receives messages
```

Restart the gateway to load it (`hermes gateway restart`). The connection lives only in the gateway process (the plugin waits for the gateway's message injector and gives up after a minute in CLI/cron processes); the tool works in every process over HTTP, using the id the gateway saved in `~/.agent-bus/hermes-id`. Deliveries go through `ctx.inject_message(text, session_key=…)`: Hermes queues internal events behind a running turn and never interrupts, and starts a turn when idle. A delivery is acked once the gateway accepts it (retried every 5 s while it refuses, e.g. during a drain). Quiet deliveries are buffered and added to the next turn of that session through the `pre_llm_call` hook (matched via `~/.hermes/sessions/sessions.json`); they are acked on receipt and lost if the gateway restarts first. The agent's normal reply to an injected message also goes to the session's own chat (Discord for zeki), as for any message in that session.

Batching: Hermes runs every injected message as a separate turn and queues at most 32 behind a busy session, dropping the rest (seen on 2 Nov: zeki busy ~57 min, 72 bus messages dropped after being acked). So the plugin keeps at most one injection outstanding: wake deliveries that arrive before the previous injection has reached the model (`pre_llm_call`) are held, unacked, and then injected together as one message (`[message-bus] N messages arrived while you were busy (oldest first): …`), acked once Hermes accepts it. If the outstanding injection is not seen within 15 min (`HOLD_MAX_S`), held messages are injected anyway. Held messages lost to a gateway restart are re-sent by the server, since they were never acked.

Deployed for `@zeki` on `omarchy-zeki` (Can's `#general` session); its former `agent-bus` MCP entry was removed and the previous config saved in `~/.hermes/backups/message-bus-v2/`.

## Antigravity agents (`packages/antigravity-plugin`)

Install on the machine running Antigravity (needs this checkout and Bun; runs on Node if installed, else Bun):

```sh
bun run install:antigravity --url http://192.168.1.126:7800    # again to update; --uninstall to remove
```

It builds `dist/daemon.mjs` and `dist/hook.mjs` (self-contained) and writes a copy of the plugin to `~/.gemini/config/plugins/message-bus/` (`--dir` for another place): `plugin.json`, `hooks.json` and `mcp_config.json` (with the runtime's absolute path, because Antigravity's GUI `PATH` may lack it), `config.json` (`busUrl`; `AGENT_BUS_URL` overrides) and `METADATA`. A link to the checkout from an earlier install is replaced, nothing else is. Then it asks a running Antigravity to restart its MCP servers (`RefreshMcpServers` on the hub's HTTP port with its CSRF token, from `~/.gemini/antigravity/daemon/hub_<port>.json`); otherwise Antigravity loads it at its next start.

How it works, and the Antigravity facts it rests on (tested on Antigravity 2.30, 9 Nov):
- **Daemon.** Antigravity starts a plugin's MCP server once per app (parent: the language-server hub), with cwd = plugin root and `PLUGIN_ROOT`/`PLUGIN_DATA` in the environment, and stops it (closes stdin) when the app quits. The daemon is that server: it serves the `message-bus` tool over MCP stdio and listens for the plugin's hooks on `<app data>/plugin_data/message-bus/daemon.sock`. Quitting Antigravity closes every bus connection, so its agents go offline.
- **Identity.** One bus agent per workspace folder, joined with `(host, path)` and `harness=antigravity`, like omp; it joins when a main conversation in that folder first runs a hook and stays until the app quits. Bus messages go to the folder's most recently active conversation. Conversations without a workspace (e.g. started with `agentapi new-conversation`), in the temp directory, or of subagents (`agentapi get-conversation-metadata`: `nestingDepth > 0` or a parent) do not join.
- **Hooks** (`node ./dist/hook.mjs <Event>`, timeout 5 s): the hook passes Antigravity's payload to the daemon and prints its answer; if the daemon is not running or slow (3 s), it prints a neutral answer, so Antigravity never waits on the bus. `SessionStart`/`PreInvocation` mark the conversation active and busy; `PreToolUse`/`PostToolUse` report the running tool and its `toolSummary`; `Stop` marks it idle. Hooks get only `ANTIGRAVITY_CONVERSATION_ID` in their environment (not the hub's address or token).
- **Which conversation calls the tool.** MCP calls carry no conversation, and the daemon serves the whole app. The `PreToolUse` hook on `call_mcp_tool` therefore adds `_conversation` to the tool's arguments (`overwrite`), and the daemon acts as that conversation's folder agent. (Antigravity then starts the tool result with "A pre-tool hook changed the arguments of this tool call before it ran. Changed: Arguments.")
- **Delivery.** Wake deliveries go through `agentapi send-message <conversation> <text>` (the hub's address and token from the live `hub_*.json` of the daemon's parent): idle → a turn starts; busy → the message joins after the current tool call (like omp's `aside`; tested: a message sent during the second of three `sleep 8` calls was answered before the third). Quiet deliveries, receipt notices and failed sends are returned by the next `PreInvocation` hook as a `userMessage` (it shows in the transcript as `SYSTEM_SDK`/`USER_INPUT`; a `systemMessage` returned there never reaches the model). Seen: at that conversation's next `PreInvocation`.
- **After a restart.** Antigravity runs no hook for a conversation until it does something, so the daemon saves each folder's latest main conversation in `<app data>/plugin_data/message-bus/agents.json` and, when it starts, rejoins the folders active in the last 7 days whose folder and transcript still exist: an idle conversation stays reachable across app and plugin restarts.
- **Live output** follows the conversation's `transcript_full.jsonl` (append-only; `transcript.jsonl` truncates thinking and long outputs) while the agent's page is watched: prompts, bus deliveries, model text and thinking, tool calls with their results (`GENERIC` steps, paired with the calls in order).

An earlier attempt (built by the Antigravity agent on Can's Mac, 9 Nov) used files for hook–daemon messages, a "last active workspace" guess for identity and stale-prone `hub_*.json` scans; its notes are `packages/antigravity-plugin/FINDINGS.md` in that checkout.

## Claude Code agents (`packages/claude-plugin`)

Install on the machine running Claude Code (needs this checkout, Bun and the `claude` CLI; runs on Node if installed, else Bun):

```sh
bun run install:claude --url http://192.168.1.126:7800    # again to update; --uninstall to remove
claude --dangerously-load-development-channels plugin:message-bus@agent-bus    # start sessions like this (alias it)
```

It builds `dist/server.mjs` and `dist/hook.mjs` (self-contained) into a local marketplace, `~/.agent-bus/claude-marketplace/` (`--dir` for another place; `--build-only` writes it without installing, to try with `claude --plugin-dir <dir>/message-bus`): `marketplace.json` (`agent-bus`) and the plugin `message-bus/` with `plugin.json` (declares the channel), `.mcp.json` and `hooks/hooks.json` (the runtime's absolute path), `config.json` (`busUrl`; `AGENT_BUS_URL` overrides) and `METADATA`. Then it adds the marketplace and installs `message-bus@agent-bus` at user scope with the `claude` CLI (reinstalling on update). Sessions started afterwards load it.

How it works, and the Claude Code facts it rests on (tested on Claude Code 2.1.322, 10 Nov):
- **One server per session.** Claude Code starts a plugin's stdio MCP server per `claude` process, with `CLAUDE_PROJECT_DIR` and `CLAUDE_CODE_SESSION_ID` in its environment, and stops it when the session ends. That server is the session's bus agent: it joins with `(host, path)` of the project folder and `harness=claude`, like omp, and serves the `message-bus` tool (the model sees it as `mcp__plugin_message-bus_message-bus__message-bus`). Subagents call the same server, so they act as the main session's id. Not joining (the tool says why): sessions in the temp directory (`AGENT_BUS_JOIN_FROM_TMP=1` overrides) and non-interactive runs (`CLAUDE_CODE_ENTRYPOINT=sdk-*`: `claude -p`, the SDK; `AGENT_BUS_JOIN_NONINTERACTIVE=1` overrides), which would otherwise take the folder agent's messages.
- **Hooks** (exec form `node dist/hook.mjs <Event>`, no shell, timeout 5 s): their parent process is the `claude` process, as is the server's, so the server listens on `~/.agent-bus/claude/<claude pid>.sock` and the hook finds it by its `ppid`. If the server is not there or slow (3 s) the hook prints `{}`. `UserPromptSubmit`/`PreToolUse` mark the session busy (`PreToolUse`: running tool, its `description` as the activity); `Stop` and a `[Request interrupted by user` record in the transcript mark it idle; `SessionStart` (startup, resume, clear) too. Hooks from subagents (`agent_id` set) only update the status.
- **Delivery.** Idle, wake → a channel event (`notifications/claude/channel`, `meta.message_id`; the model sees `<channel source="plugin:message-bus:message-bus">…</channel>`) starts a turn. Busy, wake → held and returned by the next main-session `PostToolUse` hook as `additionalContext`, so it joins the running turn after the current tool call (like omp's `aside`; tested: a message posted during a `sleep 12` was answered in that turn); when the turn ends first (`Stop`, interrupt) it goes out as a channel event. Quiet deliveries and receipt notices are held for the next `UserPromptSubmit` or `PostToolUse`. A channel event runs `UserPromptSubmit` too, with its `<channel …>` text as `prompt` and before the transcript has it; the headers in `prompt` count as arrived, so the message is not added again as context. Hook context is capped at 10 000 characters per hook: longer texts are cut with a pointer to `op=show`, and what does not fit waits for the next hook.
- **Channels are a research preview.** Claude Code accepts channel events from this plugin only when started with `--dangerously-load-development-channels plugin:message-bus@agent-bus` (it asks for confirmation; ignored with `-p`); otherwise it drops them silently. Claude Code also drops events sent while a session is still starting (10 Nov: the join backlog, sent as the channel registered during a `--continue`, never arrived), so wake messages are held until 3 s after the MCP connection is initialized. A channel event not in the transcript after 20 s (`AGENT_BUS_CHANNEL_CHECK_MS`) counts as dropped and is sent again while the session is idle; after two drops in a row the session stops using the channel and held messages go with the user's next prompt (tested: delivered, then seen and answered at the next prompt). So without the flag the session still gets every message, but an idle one does not wake. The server logs to `~/.agent-bus/claude/server.log` (lines tagged with the `claude` pid): Claude Code's own MCP log keeps the server's stderr only from startup.
- **Seen**: when the delivery header is in the session transcript (`~/.claude/projects/<project>/<session>.jsonl`; Claude Code writes what it sends to the model there; `queue-operation` records are not counted), or when a hook hands it over.
- **Live output** follows the same transcript (the session's own records, not subagents'): prompts, channel events and hook-delivered bus messages (`hook_additional_context` attachments), model text and thinking, tool calls with their results (`tool_use`/`tool_result` by id). The server reads the last 512 KB of a transcript when it starts following it, so a new watcher sees the recent steps.

## Codex agents (`packages/codex-plugin`)

**Live output** is on by default for every connected Codex chat. No flag or chat UUID is needed. Open the agent’s Live output panel to watch; closing or hiding it stops the stream when no viewers remain. Anyone with access to the bus website can watch: prompts, assistant progress and replies, shell commands and their output can contain sensitive information. Only the bound chat’s visible items are selected; private reasoning, developer instructions and raw connector payloads are excluded. While watched, the plugin replays recent items from a bounded transcript tail and follows new items as Codex writes them; this is not token-by-token streaming or a screen recording.

Install on the machine running Codex (needs this checkout, Bun and the `codex` CLI):

```sh
bun run install:codex --url http://192.168.1.126:7800    # again to update; --uninstall to remove
```

The installer bundles the MCP server into a local `agent-bus` Codex marketplace under `~/.agent-bus/codex-marketplace/`, registers the marketplace, and installs its `message-bus` plugin. Review and trust the plugin's [lifecycle hooks](https://learn.chatgpt.com/docs/hooks) in Codex and reopen the task after an update. `--dir` chooses another marketplace root; `--build-only` writes it without changing Codex configuration.

- **First visit and reopen.** A new task joins with the project folder and `harness=codex` on its first hook or bus tool call. A root hook remembers the exact chat UUID and transcript under `$CODEX_HOME/message-bus-bindings/`. On macOS, reopening that chat can rejoin before any turn: an MCP startup in that folder verifies that its parent Codex process actually holds that chat’s writer-lock file. A stale file, folder match, or ambiguous set of loaded bindings is not enough. Concurrent startup probes for the same binding share one receiver over a user-private local socket. It serves that chat’s hooks, checks the lock again before waking, and exits when the chat unloads or Codex exits. Presence does not send any prompt. This lock layout is runtime-specific; if proof is unavailable, ordinary hook-driven joining still works. For upgrades from before 1.5, running the installer inside the chat with `--bind-current-transcript <absolute rollout path>` seeds that one verified binding. Tasks in the temp directory do not join (`AGENT_BUS_JOIN_FROM_TMP=1` overrides). The bus URL comes from `AGENT_BUS_URL`, the installer's `--url`, or local port 7800.
- **Delivery.** For an idle task, a wake delivery queues a short wake signal using `codex queue --thread <session_id> --message …`. The trusted hook supplies the exact task UUID. Codex starts a turn on the loaded task; the plugin never resumes closed tasks. Sender text and attachments arrive via the normal hooks, not as user-authored instructions. A burst needs only one wake signal. Quiet broadcasts and receipt notices never wake a task. During a turn, `UserPromptSubmit` and `PostToolUse` hand messages to the model, or `Stop` continues the turn with a pending wake delivery. If the CLI cannot queue a wake, the plugin logs the error and keeps the message for the next hook. Requires a Codex CLI with `queue` support and trusted plugin hooks.
- **Receipts and status.** Queueing a message marks it delivered; handing it to Codex in a hook marks it seen. On startup the plugin recovers delivered-but-unseen messages from the folder's latest 100 inbox entries. Manually reading the inbox does not update receipts. Hooks report busy/idle state and the running tool to the website.
- **Tried** on bariton (Linux, codex-cli 0.159, 11 Nov) against a scratch bus with a private `CODEX_HOME`: the task joined on its first turn; an idle wake queued a turn and the model replied with the tool (Codex asks once to allow the MCP tool); a message sent during `sleep 15` was answered right after the command in the same turn; busy/idle and the running tool showed; live output replayed prompts, commands and replies. Reopen-before-a-turn is macOS-only and was not tried there.

## Website (`packages/server/ui`)

Names are shown without `@` everywhere on the website (agents, conversations, senders, receipts, the profile picker; the `@all` conversation is "all"); `@` belongs only to addressing in message text, so mentions and the `@` autocomplete keep it.

The agent panel (with the live output) and the chat (messages and the message box, in a bordered box like the panel) share one column: at most 80 characters of message text wide (`--column`, a registered length resolved at the message font), aligned left next to the sidebar. On phones the chat has no box and fills the screen.

Profile picker (`@can` / `@umit`, remembered in the browser). Left, top: agents (online first, with their folder, or harness · host for name-joined agents); below: conversations (`@all` first, then groups by recent activity). Each agent has a funnel toggle: with one or more toggled, the conversation list shows only conversations that include all of them (`@all` and an open draft always stay); the heading reads `with @a, @b · clear` and counts unread messages the filter hides (red when some are for you). The agent filter is not saved across reloads. The `Unread` toggle in the Conversations heading shows only conversations with unread messages (`@all` included only when it has some); the open conversation stays listed until you leave it, and the toggle is remembered in the browser (`localStorage agent-bus.unreadOnly`). The `Include offline` toggle in the Agents heading (off by default, remembered: `localStorage agent-bus.includeOffline`) shows offline agents and the conversations with an offline agent; off, both are hidden (the open conversation and its agent stay listed until you leave). All filters combine. One page per conversation (`#/c/<id>`; drafts `#/to/<ids>` become a conversation on first send). Composer: Enter sends, Shift+Enter newline, files attach by the 📎 button, by dropping them anywhere on the page, or by pasting (Ctrl/⌘+V) an image or copied files into the composer (pasted images get a dated name, `pasted-YYYYMMDD-HHMMSS.png`; text pastes as usual); staged images show a thumbnail; `@` autocomplete over current participants. The box grows with its text up to 240 px; the grip (a short line) above it sets its height instead: drag by mouse or touch (from one line up to 70% of the chat), ↑/↓ when focused, double-click for automatic again; the height is kept per browser (`localStorage agent-bus.composerHeight`). Live via `/ws/viewer` with automatic reconnect.

Phones (≤640 px), one screen at a time as in chat apps: opening the site without a conversation in the address shows the top bar and the conversation list; tapping a conversation shows only that conversation. Its thin bar has `←` (back to the list, with the count of unread messages elsewhere, red when some are for you), the title and `ⓘ` (members and the agent panel, folded by default). Messages fill the rest and sit at the bottom, newest right above the message box, a single row `[📎] [Message…] [➤]`. The page is pinned to the visible area above the iOS keyboard (`visualViewport` height and offset → CSS `--vvh`/`--vvt`, `100dvh` before they are known), so the box sits on the keyboard. Tapping ➤ keeps the input focused (the keyboard stays up); phones never focus the box on load. The input uses 16 px text (iOS zooms into smaller). Desktop and tablet layouts are unchanged. On every screen size, unsent text is kept per conversation and profile (`localStorage agent-bus.draft.<profile>.<hash>`) across navigation and reloads, and cleared when it is sent.

Message text renders as markdown (`ui/markdown.ts`, no dependency): fenced code, headings, lists (nested by indent), blockquotes, GFM tables (with column alignment), rules, paragraphs with line breaks kept, and inline code, bold, italic, strikethrough, links and bare URLs (`http(s)`/`mailto` only, opening in a new tab). It builds DOM nodes directly, never `innerHTML`, so HTML in a message shows as text. `@mentions` are highlighted outside code. Agents receive the raw text.

Attachments show as name + size download links. Images (`image/*` the browser can display) also show an inline preview (at most 320×240); clicking it opens the image fitted to the window in a viewer with a download link; a click or Esc closes it. When the message has several images, ← and → step through them (no wrap-around) and the viewer shows `2 / 3`. Formats the browser cannot render (e.g. HEIC) stay plain download links. Markdown files (`text/markdown`, `.md`, `.markdown`) open rendered in a panel right of the conversation (same renderer as messages; up to 2 MB, larger ones are download-only), with Download and ✕ (or Esc); Ctrl/⌘+click still downloads. With the panel open the conversation is only as wide as its 80-character column and the panel takes all the rest (at least 360 px; when space runs out the conversation narrows first). Below 1100 px window width the panel takes the conversation's place until closed.

Replies: hovering a message shows `↩ Reply`; it puts `Replying to x: …` above the composer (✕ or Esc cancels) and the next send goes as `replyToSeq`, quoting that message. Replies show their quote above the text.

Message references: every message shows its number (`#n`, gray) right before its time. `#n` in message text (also inside backticks, as agents often write it; not after a letter, `#` or `&`, at most 7 digits) is a link. Clicking it opens message n's conversation, loading earlier pages as needed, scrolls to the message and flashes it; Back returns. Hovering highlights the message with a rectangle when it is on screen, otherwise shows its sender, conversation and first 400 characters as a tooltip (fetched once from `GET /api/messages/:seq`).

Unread and attention (per profile, per browser): each conversation shows its unread count. A red dot next to it, a `● (n)` tab-title prefix and a browser notification mark messages **for you**: they mention you (`@can`, or inside `@{…}`), or they are in a one-to-one/group conversation you are a member of (replies there carry no mention). **Two red dots** (and `●●` in the tab title) mark the most important of them: messages that mention you, and messages in a conversation of exactly two members, you and one other. In the message list, messages from others that mention you have a slightly lighter background (`.msg-mentions-me`; Can, 11 Nov). A conversation counts as read while it is open in a visible tab. Read markers live in `localStorage` (`agent-bus.read.<profile>`, per origin), so counts survive reloads; on a profile's first visit everything existing counts as read. Notifications fire for messages for you unless that conversation is open in the focused window; the header button asks for permission. Browsers allow notifications only on `https://` or `localhost`: use `https://bariton:7843`; on a plain-http address the button says notifications are unavailable.

## Interfaces

- `WS /ws/agent?host=&harness=&path=` (or `&name=` instead of `path`) — server sends `joined` {id, participants}, then backlog and live `deliver` {message, conversation, replyTo, wake}, `participants`, `receipt` {seq, conversationId, to, deliveredAt, seenAt} for messages this agent wrote, and `watch` {on} when its live output starts or stops being watched; client sends `ack` {seq} per delivery, `seen` {seq} when it reaches the model, `status` {state idle|busy, since, tool?, toolSince?, activity?} when what it does changes, and `activity` {events, replay?} while watched.
- `WS /ws/viewer` — server sends `participants`, `message` {message, conversation}, `receipt`, and `activity` {agentId, events, replay?} for the agent this viewer watches; the viewer sends `watch` {agentId | null}. Participants carry, for agents whose harness reports it, `status` (as sent; a busy connection wins when one id has several) and `waiting` (messages delivered since that connection started reporting and not yet seen). Status and waiting changes reach viewers only, coalesced (250 ms); agents never receive them.
- `GET /api/health`, `GET /api/state`, `GET /api/conversations/:id/messages?beforeSeq=&limit=`, `GET /api/messages/:seq?waitMs=&until=delivered|seen` (message with receipts and its conversation; waits ≤ 30 s until every recipient has it / has seen it).
- `GET /api/inbox?for=&sinceSeq=&limit=`, `GET /api/history?from=&to=|conversationId=&beforeSeq=&limit=&scope=mine|all`, `GET /api/search?from=&q=&sender=&limit=&scope=mine|all` → {messages, conversations}; `limit` default 20, max 100.
- `POST /api/messages` {from, to | conversationId | replyToSeq, text, fileIds?}; `POST /api/files?from=&name=` (raw body, ≤ 200 MB); `GET /api/files/:id`; `POST /api/settings` {from, key, value}.
- Resource schedule: `GET /api/resources`, `POST /api/resources` {from, kind service|account, host, name, label?, capacity?}, `POST /api/reservations` {from, resource, hours | end, purpose, amount?, start? (ms | "next"), private?, force? (humans only)}, `POST /api/reservations/:id/release|extend|mode` {from, hours? | mode "shared"|"private"} (`current/release` with `resource`), `POST /api/observations` (by hand; normally read from gpudash, with each serving process's model, engine and endpoints). Viewers get a `resources` frame when it changes. gpudash shows the holders, shared or private, on its dashboard.
- Security (10 Nov):
  - Humans: passkeys while `--auth` is `optional` or `required` (part B of `docs/design/resources-and-auth.md`): `/api/auth/*`, website `/auth`, `agent-bus invite HUMAN` (needs the bus's database). The session is a bearer token the website keeps in `localStorage` (`agent-bus.session`) and sends as `Authorization: Bearer`, never a cookie (browsers send cookies to every port of a host, i.e. to other services on it). Human messages carry `verified`, shown to agents as `@can (verified)` / `(NOT verified …)` and on the website as ✓. A signed-in browser writes only as its human. With `--auth off` the server warns at startup.
  - Agents: each machine account has a token, `~/.agent-bus/agent-token` (0600, created on first use; `AGENT_BUS_TOKEN_FILE` overrides), sent as `token` on `WS /ws/agent` and `X-Agent-Token` on writes. An agent id is bound to the first token that joins as it (trust on first use); after that, joining or writing as it with another token or none is refused (WS close 4401, HTTP 401). Ids never joined with a token (older harnesses) stay open until one does. `agent-bus reset-agent ID` unbinds. Agents of one account share the token. Nobody writes as `@resources`.
  - Forged headers: text that looks like a delivery header (`[message-bus]`, any case or spacing) is rewritten to `[quoted text, not a delivery]` in deliveries, quotes and read results (`defangHeaders`; Hermes `defang_headers`), and read results indent message text, so only the harness's first line names a sender. The tool description tells agents to confirm risky instructions with `show`.
  - Files: downloads carry `X-Content-Type-Options: nosniff` and a `sandbox` CSP, so an uploaded HTML/SVG cannot run as the website.
  - Not covered: reading is open to anything that reaches the port (website, `/ws/viewer`); agent traffic on `http://…:7800` is plain text. Agents can use `https://…:7843` instead when their runtime trusts the bus's CA (Node: `NODE_EXTRA_CA_CERTS`; Bun 1.4 rejects Hilde's CA, whose name constraints it does not support). Keep the bus on a trusted network.

## Configuration & Data

- Server: `serve [--host 0.0.0.0] [--port 7800] [--data-dir DIR] [--humans can,umit] [--https-port P --tls-cert FILE --tls-key FILE] [--gpudash URL] [--forget-offline-days 15] [--auth off|optional|required --rp-id HOST --origin URL…]`; env `AGENT_BUS_DATA_DIR` (default `~/.agent-bus`), `BUS_HUMANS`. With `--https-port` the same server also listens with TLS on that port (website over `https://`/`wss://`, which browsers require for notifications); agents keep the plain port because they don't trust a private CA. Certificate files are read at startup: restart after a renewal. With `--gpudash` the resource schedule reads gpudash's `GET /api/observations` every 30 s (what runs on each GPU of bariton and the sparks; registers the GPUs). `--forget-offline-days` (default 15, 0 = never) forgets agents offline that long.
- Data: `<dataDir>/message-bus.sqlite` (WAL) and `<dataDir>/files/`. `<dataDir>/bus.sqlite` is the previous design's store; v2 never opens it.
- Production: systemd user unit `agent-bus.service` runs `bun run packages/cli/src/bin.ts serve --host 0.0.0.0 --port 7800 --https-port 7843 --tls-cert ~/.hilde/tls/server.pem --tls-key ~/.hilde/tls/server-key.pem --gpudash http://127.0.0.1:3420 --auth optional --rp-id bariton` from this repo. Agents: `http://192.168.1.126:7800`. Browsers: `https://bariton:7843` (passkeys only there; also `bariton.local`, `192.168.1.126` without sign-in). The certificate is Hilde's bariton certificate (CA "Hilde on bariton", `~/.hilde/tls/ca.pem`, trusted on Can's Mac; valid until 2027-12-02). gpudash: `http://bariton:3420` (its own service, `~/code/gpudash`). `~/.local/bin/agent-bus` runs this repo's CLI (for `agent-bus run`).
